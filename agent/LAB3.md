Проект: консольный менеджер задач. База: ветка lab2, коммит 9177526; изменения реализованы в lab3. Сохранены цикл и пять инструментов ЛР №2. Добавлены персистентные сессии, две стратегии сокращения истории и поиск по документации.

## Сессии

Session сохраняет JSON в agent/sessions/<id>.json заменой временного файла. Сохраняется ход пользователя, затем каждый завершённый шаг (все результаты tool_calls одного ответа вместе). При загрузке код подставляет текущий system ровно один раз. Ключ из настроек не включается в историю; его буквальное значение в строках при сохранении маскируется. JSON сессий игнорируется Git. Сохраняется рабочее окно модели: удалённые ходы после успешного сокращения не архивируются. Тест восстановления загрузил диалог в новый список с новым system и прежним сообщением пользователя.

Проверка с моделью: запустить с одним ID, сообщить имя и цель, выйти через /exit, запустить снова с тем же ID и спросить имя и цель. Идентификаторы сессий разделяют диалоги, база задач проекта общая.

## Сравнение на одном сценарии

Входные история, корпус и задача совпадают для обеих стратегий. Перед каждым прогоном создаётся отдельная временная песочница. Исходная история содержит имя, цель и длинный ответ; далее запрошены поиск приоритета, добавление двух задач и вывод незавершённых. Бюджет — 2184 условных токена. Оценка — округлённая вверх четверть длины JSON с сообщениями и схемами инструментов; аргументы и результаты вызовов тоже входят в оценку.

| 2 | add_task: Проверить отчёт | 1972 | 1972 | 1972 |

## Ответы по экспериментам

1. **Почему растёт вход?** Каждый следующий запрос содержит предыдущие вызовы и ответы инструментов. Схемы tools передаются снова. Выходные токены одного запроса не равны приросту входных токенов следующего.
2. **Что удаляет trim?** Старые ходы от user до следующего user. Первое системное сообщение и весь текущий ход остаются; ни один результат tool не отделяется от породившего его assistant.tool_calls. Если даже обязательная часть не помещается, запрос не отправляется, пользователь получает сообщение о бюджете.
3. **Что сохраняет summarize?** Краткое описание старых фактов, решений и открытых задач после system, с префиксом «[память диалога]». Это контекст от роли assistant, не новая системная инструкция. В контрольном примере сохранены имя Тимур и цель. При ошибке API, пустой сводке или отсутствии места используется trim. Если сами старые сообщения слишком велики для запроса памяти, для него сохраняются начало и конец текста: часть сведений может потеряться. Фактическое качество сводки зависит от модели.
4. **Как поиск помогает доменному инструменту?** Агент может сначала запросить search_docs, взять из результата значение mid, затем передать его в add_task. Поиск считает пересечение слов без учёта регистра, возвращает путь и до трёх подходящих абзацев на документ, всего от одного до пяти документов. Поиск ограничен workspace/docs. Embeddings не используются.
5. **Чем различаются виды памяти?** JSON сессии сохраняет рабочую переписку конкретного диалога; сводка сокращает её для модели; search_docs находит постоянные правила проекта; tasks.json содержит фактические задачи, независимо от выбранного ID сессии.

## Воспроизведение на Windows

Из корня репозитория:
```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m agent.experiment
.\.venv\Scripts\python.exe agent/agent.py --session defense --strategy summarize
```

Для сравнения стратегий с **реальным API**, после настройки agent/.env:
```powershell
.\.venv\Scripts\python.exe -m agent.experiment --live | Tee-Object -FilePath agent/experiment-live.txt
```
В режиме --live пользователь сам подтверждает каждую запись. Скрипт сохраняет задачи только во временных каталогах, реальные задачи не изменяются. Для просмотра полного интерактивного вывода при проблемах с вводом через конвейер запустите без Tee-Object. Проверьте имена моделей, usage.prompt_tokens и фактическую последовательность инструментов. Сопоставьте ответы при одной фиксированной модели, если она доступна. Число шагов живого агента заранее не гарантировано. Если обрезки не было, повторите с меньшим --budget; если текущий ход не помещается — увеличьте его. Для сдачи с требованием живых логов приложите фактический журнал и дополните таблицу показаниями usage.
